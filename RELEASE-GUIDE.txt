FASTING TRACKER — RELEASE / UPDATE PROTOCOL v1

For ordinary releases (for example 1.0.0 -> 1.0.1 or 1.5.0):

1. DO NOT modify sw.js. It is the stable update-protocol worker.
2. Bump the semantic version in all three places:
   - <meta name="ft-app-version" content="X.Y.Z"> in index.html
   - const APP_VERSION = 'X.Y.Z' in index.html
   - version in version.json
3. Keep version.json protocolVersion at 1.
4. Update version.json released/notes.
5. Update version.json shell only if public release files were added/removed.
6. Keep entry set to ./index.html.
7. Update visible footer/version text and sitemap lastmod when appropriate.
8. Run: python tools/build_release.py
   This regenerates the SHA-256 hash for EVERY update-managed shell asset.
   Do not hand-edit the hashes. HTML hashes use the documented github-pages-v1 normalization so Jekyll's site/repository URL substitutions remain verifiable.
9. Run: python tests/test_release.py
10. Deploy all changed public files in one Git commit.
11. Existing installations keep serving their active cached release until the user accepts the in-app update.
12. The stable service worker fetches/stages the complete shell with a release cache-buster, verifies every asset against version.json, verifies that index.html declares the same release version, and only then atomically switches the active release cache.

Only change sw.js if the UPDATE PROTOCOL itself needs to change. A protocol change requires deliberate compatibility planning and a protocolVersion bump; it is not an ordinary app update.

IMPORTANT: Any public app/content change that installed users must receive requires a version bump. Editing index.html without changing version.json will intentionally NOT replace an installed active release.

PROTOCOL CHANGES
Protocol changes must be backward-compatible with the currently deployed app/SW long enough for installed clients to cross the upgrade boundary. Do not simply replace protocol v1 with an incompatible message contract.

ACCESSIBILITY
Do not re-add a forced portrait orientation unless there is a compelling requirement; the responsive app intentionally allows device rotation.
