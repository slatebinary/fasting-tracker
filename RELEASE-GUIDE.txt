FASTING TRACKER — RELEASE GUIDE

Ordinary release process

1. Start from the latest complete release folder.
2. Update APP_VERSION, the ft-app-version meta value, public About/Privacy footer versions, version.json version/date/notes, and release-specific tests.
3. Keep sw.js byte-for-byte unchanged unless the update protocol itself must change. Any protocol change must remain backward-compatible with already installed versions.
4. Run tools/build_release.py to regenerate SHA-256 hashes for every version.json shell asset.
5. Run tests/test_release.py and JavaScript syntax checks. Do not package a release unless all checks pass.
6. Package the CONTENTS as a complete release. Upload the entire release contents together so index.html, version.json, manifests and hashes cannot become mismatched.
7. After GitHub Pages deploys, verify live version.json and the app version shown in Settings.

Data-safety rules

- Main fasting/weight data is always higher priority than retaining the full internal snapshot schedule.
- Internal snapshots are local recovery aids, not external backups. If storage is tight, the app may keep fewer snapshots and must warn the user.
- Before update/import/restore operations that replace data, require a verified internal recovery snapshot when the workflow depends on it.
- Before removing/reinstalling a Home Screen PWA (including icon changes), export an external JSON backup first.
- Do not describe persistent browser storage as surviving uninstall; it only reduces ordinary eviction risk.
