FASTING TRACKER — RELEASE GUIDE

Canonical version source

1. Edit only version.json for the release version/date/notes.
2. Make the intended source, translation and documentation changes.
3. Run tools/build_i18n_runtime.py after editing i18n/*.json.
4. Run tools/export_i18n_source.py after translation/source changes.
5. Run tools/build_release.py. It stamps the application/public-page version from version.json and regenerates the SHA-256 shell hashes.
6. Run tools/build_release.py --check and tests/test_release.py. Run the browser regressions relevant to changed behavior.
7. Complete ACCESSIBILITY-CHECKLIST.txt on real devices for releases that change UI, charts, dialogs, navigation or accessibility.

GitHub Pages deployment

- The repository includes .github/workflows/pages.yml. It validates the committed release, runs the release gate, builds a deployment-only _site artifact, and then deploys that artifact.
- In GitHub repository Settings -> Pages, select GitHub Actions as the publishing source before relying on this workflow.
- Do not publish a partially uploaded working directory. A release is valid only when version.json, index.html, helper scripts, translations, manifests and integrity hashes belong to the same committed release.
- After deployment, open the live app and run Settings -> Updates -> Check. Data & storage health should report matching live metadata and live entry versions.

Data-safety rules

- Main fasting/weight data is always higher priority than retaining the full internal snapshot schedule.
- Internal snapshots are local recovery aids, not external backups. If storage is tight, the app may keep fewer snapshots and must warn the user.
- Before update/import/restore operations that replace data, require a verified internal recovery snapshot when the workflow depends on it.
- Before removing/reinstalling a Home Screen PWA (including icon changes), export an external JSON backup first.
- Do not describe persistent browser storage as surviving uninstall; it only reduces ordinary eviction risk.
- CSV files are data exports, not the canonical restore format. The JSON backup or Export Everything bundle contains the restorable backup.

v1.11.x stability policy
- Do not change DATA_VERSION or IndexedDB schema during the 1.11.x stabilization line unless required to fix a concrete correctness/data-loss issue.
- Run REAL-IPHONE-CHECKLIST.txt before designating a 1.11.x build as stable for iPhone Home Screen use.
- Last-known-good status is recorded only after local integrity verification passes.

Single-user rolling compatibility policy
- Storage generation 3 is the current record-store layout.
- Direct startup migration supports the current generation plus the previous two generations only (currently generations 1-3).
- External JSON import supports the current backup format plus one older backup generation (currently v1-v2).
- Obsolete internal recovery-snapshot formats are not long-term compatibility targets; external JSON is the durable recovery format.
- After a successful legacy migration, delete the obsolete primary/localStorage payload so the legacy path is not exercised again.
- When STORAGE_GENERATION advances, reassess and prune code/tests that fall below MIN_DIRECT_STORAGE_GENERATION.
